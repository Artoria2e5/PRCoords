PRCoords test vectors
=====================

These are reference outputs generated by the Python implementation, which is
the canonical one here: CPython does its floating-point arithmetic the dumb,
faithful way, and the other implementations are checked against it.

Everything in this directory is generated; run `python py/gentest.py`
from anywhere to refresh all five files.

Files
-----

* `inputs.tsv`: two columns, the input WGS-84 `lat` and `lon`.
* `vec.tsv`: eight columns, the input pair followed by the results of
  `wgs_gcj`, `gcj_bd` and `wgs_bd` as applied *to the input pair*. The
  `gcj_bd` column treats the input as GCJ-02 coordinates, not as the GCJ-02
  result of the first column.
* `vecs.f64.bin`: the same data as `vec.tsv`, as little-endian IEEE-754
  doubles in file order, eight per record (64 bytes each):

      struct point { double lat, lon; };       // degrees, 16 bytes
      struct tv { point in, w_g, g_b, w_b; };  // 64 bytes

* `cusp.tsv`, `cusp-inputs.tsv`: the same two layouts, holding 35N 105E and
  a two-sided sweep of deltas from 1e-2 down to 1e-12 deg around it.

The points in `vec.tsv` trace the border of China, where the distortion field
is the most interesting. The 105E 35N origin of the deviation polynomial is
*not* among them: it sits on the cusp of a `sqrt(abs(x))` term, so the
derivative is infinite there and a vector at that point tests the exact
expression rather than the arithmetic. It gets its own set, with a two-sided
sweep down to 1e-12 deg. The last few deltas are below single precision, so a
`float` build sees them all as plain 105.

Checking an implementation
--------------------------

Each implementation ships a small dumper that reads "lat lon" pairs from a file
or stdin and writes the same eight columns to stdout:

    cpp/vecs TestVecs/inputs.tsv
    node js/vecs.js TestVecs/inputs.tsv

`py/checkvecs.py` compares such a dump with `vec.tsv`, either by running the
command itself or by reading its output:

    python py/checkvecs.py --run "cpp/vecs" --profile badmath
    node js/vecs.js | python py/checkvecs.py - --profile exact
    python py/checkvecs.py --run "cpp/vecs" --set cusp

The last one reads `cusp.tsv` and `cusp-inputs.tsv` instead, and says so.
`--ref` and `--inputs` override the pair by hand. Add `-v` to list every row
instead of just every transform, which is how you watch a sweep row by row.

The tolerances are in degrees, and each profile says how sloppy the build is:

| profile         | largest deviation | for                                           |
|-----------------|-------------------|-----------------------------------------------|
| `exact`         | 1e-12             | double or long double with IEEE `sin`         |
| `badmath`       | 1e-8              | double with the `badmath::sinpi` minimax fit  |
| `float`         | 3e-5              | `PRCOORDS_NUM=float` with IEEE `sin` (~2.4 m) |
| `float-badmath` | 3e-5              | both of the above                             |

Measured against the current C++ and JS implementations, the approximate build
lands at 8e-10 deg (0.09 mm), the 32-bit one at 2.1e-5 deg (2.3 m), and the
exact builds at zero to the last bit. That leaves the profiles some room for
compiler wobble and other libms. A `float` build cannot do much better than
1e-5 deg however faithful the math, which is why it gets its own row.

Round trips
-----------

The inverse functions here subtract the forward offset instead of solving for
it, so a round trip leaves 4e-7 to 3.5e-5 deg of residue over the vectors above
(0.05 m to 3.9 m, the worst at 47.80N 131.0E). That residue does not grow at
cusp: it stays at 1.8 m over the whole `cusp.tsv` sweep, because the inverse
evaluates the offset at a point some 300 m away from the singularity. These
vectors are forward only; if you need the inverse checked, do it in each
implementation.

Commands given to `--run` go through the shell, so on Windows use
`cpp\vecs` instead of `cpp/vecs` for the executable name.
